チャイム不鳴動の懸念について、対応方針と検証結果をご報告します。

## 原因

ご指摘の通り、`/display_data` がDBエラー時に `calling: []` を返す実装のままだと、フロント側の `prevCallingKeys`(呼出し検知用の差分)がその瞬間にリセットされてしまいます。その直後に本当の新規呼出しが発生すると、直前の状態が「空」だったことになっているため「初回読み込みと同じ」と判定され、チャイムが鳴らなくなります。

## 対応

`/display_data` にサーバー側のキャッシュを導入しました。DB取得に成功するたびに直前の正常値を保存し、DBエラー発生時はそのキャッシュ値をHTTP 200でそのまま返します。

```python
_display_data_cache = {'calling': [], 'waiting_count': 0}

@app.route('/display_data')
def display_data():
    global _display_data_cache
    try:
        with get_db() as conn:
            # ... DB取得処理 ...
        _display_data_cache = {'calling': calling, 'waiting_count': waiting_count}
    except Exception as e:
        print(f"[display_data] DB error, returning cached data: {e}")
    return jsonify(_display_data_cache)
```

これにより2点とも解消されます。

- **表示継続**: 待ち人数「3」の状態でDBエラーが起きても、画面には「3」が表示され続けます(「0」に一瞬落ちてから戻る、という混乱がなくなります)。
- **チャイム**: DBエラー時のレスポンスが直前の正常値と完全に一致するため、`prevCallingKeys` が誤ってリセットされません。フロント側のコードは無改修のままで、この副作用を解消できます。

## 検証

`verification/test_display_data_cache.py` にて、以下の3段階を検証しました。

1. 起動直後(キャッシュがまだ無い状態)でDBエラー → 空の初期値を200で返す
2. 呼出し中(番号1)の状態でDBエラー → キャッシュされた「番号1呼出し中」がそのまま200で返る
3. **エラー発生の直後に、本当に番号2が新しく呼び出された場合** → 次のポーリングで「番号1」に「番号2」が正しく追加された状態が返り、番号1が消えたり、一度空になってから2件出たりしない

3番目が今回ご指摘いただいたシナリオそのものです。エラーを挟んでも見た目上の遷移は「[1] → [1, 2]」という自然な追加になり、フロントの差分検出にとって「初回読み込み」に見えることはありません。

## 補足

- 障害の発生自体は `except` 内の `print` ログに残る形のままです。職員・管理側での検知手段(監視やアラート)は今回のスコープ外としており、必要であれば別issueとして切り出す想定です。
- 実装はFlask開発サーバーでの単一プロセス運用を前提にしています。gunicorn等の複数ワーカー構成にする場合、ワーカーごとにキャッシュが分かれるため別途対応が必要です(現状は単一プロセス運用とのことなので、いったんこのままで問題ないと考えています)。

この内容で問題なければ、いつも通りブランチ(`fix/db-error-http-status`)でお待ちしておきます。必要であればPRを出します。
